Professional Website Deployment

A guided course for taking a finished website from a developer's computer to a secure, discoverable, monitored production service. Covers DNS, HTTPS, cloud infrastructure, Google Cloud, AWS, Microsoft Azure, databases, SEO, deployment automation and long-term operations.

Beginner → production-readyWindows + VS CodeHTML · CSS · JavaScriptNode.js / .NET · PostgreSQL

How to use this course

Work through the modules in order. Each module explains the concept, why it matters, what you need, and what you should be able to demonstrate before moving on.

Course outcome: you should be able to deploy a static frontend, publish a backend API, connect it securely to a managed database, attach a custom domain, enable HTTPS, configure search indexing, and operate the live site.

This guide uses a representative application: a school or business website with public pages, a registration/admissions form, an API, PostgreSQL and email notifications. Adapt the data model and security controls to your actual application.

Important: Google Cloud, AWS and Azure are three alternative cloud platforms. You normally choose one provider for a given deployment rather than deploying the same beginner project to all three. Learn the concepts once, then practise the provider-specific method you select.

Cloud product names, pricing, free tiers, supported regions and quotas can change. Verify them in the provider's live documentation and pricing calculator before creating billable resources. No cloud service is guaranteed to be free.

1. Understand the production architecture

A production website is a set of cooperating services. The browser downloads the frontend; the frontend calls the backend; the backend validates requests and talks to the database. DNS directs the domain, TLS encrypts traffic, and monitoring helps you detect faults.

↓ private / controlled database connection

Supporting services: email delivery · object/file storage · logs · alerts · backups · CI/CD

Understand each layer

  • Domain: the human-readable name, such as example.com.
  • DNS: the directory that tells clients where a domain's services are located.
  • CDN / edge: caches eligible content near visitors and can provide filtering and protection.
  • Frontend: the browser-facing HTML, CSS, JavaScript, images and fonts.
  • Backend/API: server-side business rules, validation, authentication and database access.
  • Database: persistent structured records. It should not be exposed directly to public visitors.
  • Operations: deployment, logs, monitoring, backups, patching and incident response.
Do not confuse hosting with a domain. Buying a domain does not host your application. Hosting does not automatically mean your domain's DNS is configured. A certificate does not replace application security.

3. Internet and server foundations

3.1 Client, server and request

A client is software requesting a resource, usually a browser. A server is software or a machine that receives requests and provides responses. HTTP defines the request/response exchange.

Browser  ── HTTPS request ──> Web application
Browser  <─ HTTPS response ─── Web application

3.2 IP addresses, ports and protocols

  • IP address: identifies a network interface or destination, such as an IPv4 address.
  • Port: identifies a service endpoint on a host. Common defaults are HTTP 80, HTTPS 443, PostgreSQL 5432, SSH 22.
  • TCP: reliable, ordered transport used by conventional HTTPS connections.
  • TLS: cryptographic protocol that authenticates the server and encrypts traffic.
  • HTTP: application protocol used by browsers and APIs.

A port number is not a security boundary by itself. Firewall rules and application authentication still matter. Never open PostgreSQL's port to the entire internet just to make a remote connection work.

3.3 Web server, application server and reverse proxy

A web server such as Nginx or Apache can serve static files and forward dynamic requests. An application process such as Node.js or ASP.NET Core runs your business logic. A reverse proxy receives public traffic and routes it to the application. Managed platforms often provide much of this infrastructure for you.

3.4 Containers and serverless

A container packages an application with its runtime dependencies into an image. It helps make builds repeatable. A virtual machine provides a virtual computer whose operating system you manage. A managed platform runs your code while the provider manages more of the underlying servers. Serverless does not mean there are no servers; it means server management is abstracted and billing/scaling is based on the provider's model.

4. Domain registration and DNS configuration

4.1 Register a domain

  1. Choose a clear, memorable domain and check spelling, renewal price and registration terms.
  2. Register it through a reputable registrar. Turn on account MFA and domain transfer lock.
  3. Use an email address you control and keep renewal/payment details current.
  4. Decide which DNS provider will host the DNS zone. The registrar and DNS provider can be different companies.

4.2 DNS records you must recognize

CAARestricts which certificate authorities may issue certificatesOptional hardening; configure carefully.

TTL means time to live: how long a DNS answer may be cached. Lower TTL values can help during planned migrations, but they do not make all DNS changes instantly visible. DNS caches expire at different times.

4.3 Practical DNS sequence

  1. Add the domain to your chosen DNS provider.
  2. Copy the provider's assigned nameservers into the registrar if you are changing DNS authority.
  3. Wait for the delegation change to become visible.
  4. Add the exact A, AAAA or CNAME records supplied by your hosting platform.
  5. Add email MX/TXT records only when configuring domain email. Do not overwrite existing mail records accidentally.
  6. Verify the root domain and www hostname independently.
# Windows: inspect DNS resolution
nslookup example.com
nslookup www.example.com

# PowerShell: inspect selected record types
Resolve-DnsName example.com -Type A
Resolve-DnsName example.com -Type MX
Resolve-DnsName example.com -Type TXT
Do not copy sample IP addresses from tutorials into your live DNS. Use the exact values shown by your hosting provider. Some platforms use CNAME targets or verification records rather than a fixed IP address.

5. HTTPS, SSL and TLS

People often say “SSL certificate”, but modern websites use TLS. HTTPS is HTTP carried over a TLS-protected connection. TLS helps authenticate the server and protect data against interception and modification in transit.

5.1 Certificate terms

  • Certificate Authority (CA): trusted organization that issues certificates.
  • Public/private key pair: cryptographic keys used in authentication and secure key establishment.
  • Certificate: binds a public key to a domain identity for a validity period.
  • Certificate renewal: replaces an expiring certificate before it becomes invalid.
  • HTTPS redirect: sends HTTP visitors to the HTTPS URL.
  • HSTS: tells browsers to use HTTPS for future connections to the domain.

5.2 Enable HTTPS safely

  1. Attach the domain to the hosting service and complete its ownership verification.
  2. Issue or attach a trusted certificate for every required hostname, such as root and www.
  3. Confirm the certificate is valid and covers the exact hostname.
  4. Enable automatic renewal where supported.
  5. Redirect HTTP to HTTPS at the platform or web-server layer.
  6. Fix mixed content: images, scripts, fonts and API requests must not load insecurely.
  7. Test forms, login, API calls and redirects after enabling HTTPS.

Let's Encrypt provides free automated certificates. Many managed hosts issue and renew certificates automatically after domain verification.

Cloudflare proxy warning: if Cloudflare proxies requests to your origin server, encrypt both legs: visitor-to-Cloudflare and Cloudflare-to-origin. Use Full (strict) when the origin has a valid, hostname-matching certificate. “Flexible” can leave the origin leg unencrypted and can cause redirect loops in some configurations.

7. Google Cloud deployment method

Suggested path: Cloud Run for the API/application, Cloud SQL for PostgreSQL, Cloud Storage or a static hosting product for static assets, Secret Manager for secrets, and Cloud Logging for operations. Cloud Run can deploy supported language source directly or run a container image.

7.1 Required tools and resources

  • Google account and Google Cloud project with billing enabled.
  • Google Cloud CLI (gcloud) installed, or use Cloud Shell.
  • Git repository with a working app and production start command.
  • Cloud Run API and Cloud SQL API enabled as needed.
  • Cloud SQL PostgreSQL instance, database, user and backup policy.
  • Secret Manager secrets for database credentials and other private configuration.

7.2 Prepare the application

Your application must listen on the port supplied by the runtime environment and bind to the expected network interface. Do not hard-code a local development port. Keep secrets out of source control.

# Example: authenticate and select your project
gcloud auth login
gcloud config set project YOUR_PROJECT_ID

# Enable commonly needed APIs
gcloud services enable run.googleapis.com
gcloud services enable cloudbuild.googleapis.com
gcloud services enable artifactregistry.googleapis.com
gcloud services enable sqladmin.googleapis.com
gcloud services enable secretmanager.googleapis.com

API enablement may require project permissions. Follow the current Cloud Run and Cloud SQL setup guides for IAM roles and service identity configuration.

7.3 Deploy a supported source project to Cloud Run

For supported source runtimes, source-based deployment can build the application for you. Run the command from the application directory.

# Deploy from the current source directory
gcloud run deploy YOUR_SERVICE_NAME \
  --source . \
  --region YOUR_REGION \
  --allow-unauthenticated

--allow-unauthenticated makes the service publicly reachable. Use it only for a public website/API whose own routes and data are designed for public access. Private admin APIs should require authentication. For production, configure environment variables, service identity, secrets and database connectivity deliberately.

7.4 Connect Cloud Run to Cloud SQL

  1. Create a Cloud SQL for PostgreSQL instance in a suitable region.
  2. Create the application database and a dedicated database user.
  3. Configure a Cloud Run service identity with only the required Cloud SQL permissions.
  4. Configure Cloud Run's Cloud SQL connection using the current provider instructions.
  5. Store credentials in Secret Manager; reference them as secrets in the service configuration.
  6. Use TLS/secure connector configuration as recommended by Google Cloud. Do not expose the database to all public IP addresses.
  7. Run schema migrations using a controlled release process and verify the app can read/write expected records.

7.5 Domain, HTTPS and logs

Map the custom domain using the current Cloud Run domain-mapping guidance or an appropriate load-balancer setup. Add only the DNS records Google provides. Verify certificate provisioning before announcing the domain. Use Cloud Logging and Error Reporting to inspect startup failures, HTTP errors and application exceptions.

Google Cloud completion test: the Cloud Run URL responds; the custom domain resolves; HTTPS is valid; the API reaches Cloud SQL; secrets are not visible in Git; logs show no repeated errors; backups are configured.

Official guides: Cloud Run documentation · Cloud SQL for PostgreSQL · Install Google Cloud CLI.

8. Amazon Web Services deployment method

Suggested beginner path: AWS App Runner for a supported web service sourced from GitHub or a container image; Amazon RDS for PostgreSQL; Secrets Manager for credentials; CloudWatch for logs and metrics. Other valid options include Elastic Beanstalk, ECS with Fargate, or EC2. Select based on the application's needs and regional availability.

8.1 Required tools and resources

  • AWS account, billing access and an IAM identity with least-privilege permissions.
  • AWS CLI v2 if you want terminal-based administration; the AWS Console is also available.
  • GitHub repository or container image in Amazon ECR.
  • App Runner service or another chosen compute service.
  • RDS for PostgreSQL database in a suitable VPC/subnet configuration.
  • Secrets Manager, CloudWatch and a defined backup/retention plan.

8.2 Prepare your AWS account

  1. Enable MFA on the root account and do not use root credentials for daily development.
  2. Create an IAM identity/role for deployment with only the permissions required.
  3. Choose a region near the target audience where all required services are available.
  4. Create a billing budget and alerts before provisioning.
# Configure AWS CLI v2 credentials/profile
aws configure

# Confirm the active identity
aws sts get-caller-identity

# Check the configured region
aws configure get region

Do not paste access keys into source files or commit them to GitHub. Prefer short-lived role-based credentials and managed integrations where available.

8.3 Deploy with App Runner (console workflow)

  1. Push a working application to GitHub. Ensure the repository has the correct build and start instructions.
  2. Open AWS App Runner and choose Create service.
  3. Choose source code repository and connect the GitHub account through the AWS-supported connection flow.
  4. Select the repository, branch and source directory.
  5. Choose automatic deployments only if you want commits to that branch to deploy automatically.
  6. Configure the runtime, build command, start command and listening port for your language/framework.
  7. Configure environment variables and secrets using supported secure references.
  8. Review instance sizing, health checks, networking and access settings, then create the service.
  9. Wait for deployment to finish and inspect service events and logs.

App Runner builds and runs a managed service from source or a container image. If you use RDS, carefully configure networking so the service can reach the database without making PostgreSQL publicly open. Follow the current App Runner VPC connector and RDS connectivity documentation for your chosen topology.

8.4 Database and supporting services

  1. Create an RDS PostgreSQL database in a private network configuration where practical.
  2. Configure security groups to allow database traffic only from the application service's approved network path.
  3. Create a dedicated application database user with restricted permissions.
  4. Store the connection details in AWS Secrets Manager and grant the application role permission to retrieve only that secret.
  5. Enable automated backups, define retention and test a restore procedure.
  6. Use CloudWatch logs/metrics and configure alerts for errors, CPU, storage and availability.

8.5 Domain and HTTPS

Use Route 53 or your existing DNS provider. Configure the custom domain and certificate using the selected AWS service's current instructions. AWS Certificate Manager is commonly used with supported AWS endpoints. If CloudFront is used, follow its certificate-region and DNS validation requirements exactly.

AWS completion test: App Runner or the chosen compute service is healthy; the service can reach private RDS; security groups are restrictive; secrets are managed; HTTPS and custom domain work; CloudWatch shows healthy operation; backups are restorable.

Official guides: App Runner getting started · App Runner developer guide · RDS for PostgreSQL · AWS CLI installation.

9. Microsoft Azure deployment method

Suggested path: Azure App Service for Node.js or ASP.NET Core, Azure Database for PostgreSQL Flexible Server, Key Vault for secrets and Application Insights for application telemetry. Azure Container Apps is another option for container-based applications.

9.1 Required tools and resources

  • Microsoft account and Azure subscription with billing enabled.
  • Azure CLI or the Azure extension for VS Code.
  • GitHub repository and a working production build.
  • App Service plan and Web App, or Container Apps environment.
  • Azure Database for PostgreSQL Flexible Server.
  • Key Vault, Application Insights and backup/restore configuration.

9.2 Sign in and choose a resource group

# Sign in to Azure
az login

# Select the intended subscription
az account list --output table
az account set --subscription YOUR_SUBSCRIPTION_ID

# Create a resource group
az group create \
  --name rg-website-production \
  --location YOUR_AZURE_REGION

A resource group is a logical container for related Azure resources. Use clear names and tags so you can identify the resources and their environment.

9.3 Create and deploy an App Service

  1. In the Azure Portal or VS Code Azure extension, create a Web App.
  2. Choose a supported runtime stack that matches your application, such as the appropriate .NET or Node.js version.
  3. Choose Linux or Windows based on runtime and deployment requirements.
  4. Create or select an App Service plan. Understand the plan's pricing tier, memory, CPU, scaling and availability features.
  5. Deploy from GitHub Actions, the VS Code extension or the documented Azure CLI workflow.
  6. Set production application settings in App Service configuration rather than hard-coding secrets.
  7. Configure health checks, logging and Application Insights where appropriate.

For Node.js, ensure the app listens on the port provided by the hosting environment where required. For ASP.NET Core, publish the correct configuration and verify the runtime stack matches the target service.

9.4 Configure PostgreSQL and Key Vault

  1. Create Azure Database for PostgreSQL Flexible Server in an appropriate region.
  2. Choose private networking where practical; if using public access, tightly restrict allowed sources.
  3. Create the application database and a dedicated restricted user.
  4. Configure TLS for database connections according to Azure's current instructions.
  5. Store credentials in Key Vault and grant the app's managed identity permission to read only the required secrets.
  6. Configure backup retention and test restore to a separate instance or safe environment.

9.5 Custom domain and HTTPS

Add and verify the custom domain in App Service. Configure the DNS records Azure specifies, then bind a supported TLS certificate. Use HTTPS-only settings and test both the root and www hostnames. Do not assume that domain verification alone enables a secure certificate.

Azure completion test: the App Service deployment is healthy; the app can access PostgreSQL securely; managed identity/Key Vault is configured; domain verification and HTTPS work; Application Insights captures errors; backups and restore have been tested.

Official guides: Azure App Service · Deploy ASP.NET Core · Deploy Node.js · Azure Database for PostgreSQL · Azure CLI installation.

10. Deploy and protect the production database

A production database is not simply your local PostgreSQL instance copied to the internet. It needs access control, encrypted connections, backups, monitoring, capacity planning and a tested recovery procedure.

10.1 Before migration

  • Remove sample/test records and unnecessary personal data.
  • Review table relationships, primary keys, foreign keys, unique constraints and indexes.
  • Check that schema migrations can be run predictably.
  • Use a separate migration/administrative identity and runtime application identity where appropriate.
  • Store all credentials outside source control.
  • Document expected data retention and deletion rules.

10.2 PostgreSQL export and restore examples

# Export a database in custom format
pg_dump -Fc -h localhost -U postgres -d your_database -f backup.dump

# Restore into an already-created empty target database
pg_restore -h YOUR_DB_HOST -U YOUR_DB_USER \
  -d YOUR_TARGET_DATABASE --no-owner backup.dump

These are examples; supply the correct host, database and credentials. Avoid putting passwords directly in command history. Use the cloud provider's recommended secure authentication and network path. Check PostgreSQL major-version compatibility and test the restore before production cutover.

10.3 Database safety rules

  • Do not use the database superuser as the website's normal login.
  • Do not allow 0.0.0.0/0 access to PostgreSQL as a shortcut.
  • Require encrypted connections and verify certificates where supported.
  • Use parameterized SQL queries; never build SQL by concatenating untrusted form input.
  • Limit what the application account can read, insert, update and delete.
  • Enable automated backups and point-in-time recovery if supported and justified.
  • Test restore, not just backup creation.

10.4 Production configuration

Use environment-specific settings. A development connection string must never accidentally point at the production database, and production credentials must never be committed to a repository.

# Example environment variable names (values belong in a secret store)
DATABASE_URL=...
APP_ENV=production
EMAIL_API_KEY=...
SESSION_SECRET=...

Never paste real passwords, tokens, private keys or complete production connection strings into screenshots, public issue trackers or chat messages.

11. Git, staging and automated deployment (CI/CD)

CI means Continuous Integration: automatically build and test code changes. CD means Continuous Delivery/Deployment: prepare or automatically release verified changes to an environment.

11.1 Use separate environments

EnvironmentPurposeData
DevelopmentLocal coding and debuggingFake/test data
StagingProduction-like final testingSanitized test data

11.2 Basic Git workflow

git init
git add .
git commit -m "Prepare website for deployment"
git branch -M main
git remote add origin https://github.com/YOUR_ACCOUNT/YOUR_REPOSITORY.git

Before committing, create a .gitignore file and exclude secrets, local environment files, build outputs and temporary files. Review git status before every push.

11.3 CI/CD pipeline stages

  1. Developer pushes a change to a branch.
  2. Automated workflow checks out the source.
  3. Dependencies are installed using lockfiles.
  4. Linting, unit tests and security checks run.
  5. The application is built or a container image is produced.
  6. Staging deployment runs and smoke tests verify the service.
  7. Production deployment requires the chosen approval/release rule.
  8. Health checks run; a failed release triggers rollback or a documented recovery.

Store deployment credentials as protected repository/environment secrets or, preferably, use the cloud provider's supported federated identity/OIDC flow to avoid long-lived cloud keys. Restrict production deployment to trusted branches and reviewers.

12. SEO, indexing and website discoverability

SEO (Search Engine Optimization) improves how search engines understand your content and how people discover it. Technical correctness helps crawling and indexing, but no technical setting guarantees a particular ranking.

12.1 On-page SEO

  • Give every important page a unique, descriptive <title>.
  • Write a useful meta description for people deciding whether to visit.
  • Use semantic HTML and a logical heading hierarchy.
  • Write original, helpful content that matches the page's purpose and audience.
  • Use descriptive URLs, internal links and meaningful link text.
  • Add useful alternative text to informative images; use empty alt text for purely decorative images.
  • Make the site mobile-friendly and accessible by keyboard.

12.2 Technical SEO files

Example robots.txt for a public website:

User-agent: *
Allow: /
Sitemap: https://www.example.com/sitemap.xml

Example sitemap entry (replace the example domain with the real canonical URL):

<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://www.example.com/</loc>
  </url>
  <url>
    <loc>https://www.example.com/admissions</loc>
  </url>
</urlset>

robots.txt is not a privacy or security control. It gives crawlers instructions; it does not prevent someone from opening a URL. Protect private pages with authentication and authorization. Use a noindex directive where appropriate for pages that should not appear in search.

12.3 Google Search Console

  1. Open Google Search Console.
  2. Add the domain property and verify ownership using the DNS TXT record Google supplies.
  3. Submit the sitemap URL.
  4. Inspect important URLs and review indexing issues.
  5. Check mobile usability and Core Web Vitals reports when data is available.
  6. Update broken links, duplicate pages and incorrect canonical URLs.

12.4 Analytics and structured data

Use an analytics tool only after deciding what user activity you need to measure and configuring appropriate privacy notices and consent requirements. Structured data can help search engines interpret eligible content, but it does not guarantee rich results. Use only markup that accurately describes visible page content.

13. Application and infrastructure security

Security is a shared responsibility. The cloud provider secures parts of the underlying platform; you remain responsible for your application code, data, identities, configuration and the services you choose to expose.

13.1 Application security controls

  • Validate every input on the server, not only in browser JavaScript.
  • Use parameterized database queries or a safe ORM.
  • Hash passwords with a modern password-hashing algorithm; never store plaintext passwords.
  • Use secure session cookies: HttpOnly, Secure and an appropriate SameSite policy.
  • Use CSRF protections where cookie-based authentication requires them.
  • Encode output and sanitize rich text to reduce XSS risk.
  • Enforce authorization on every protected API endpoint.
  • Apply rate limits to login, registration and sensitive endpoints.
  • Limit file upload types, size, storage location and processing.
  • Keep dependencies and runtimes patched; scan for known vulnerabilities.

13.2 Infrastructure security controls

  • Enable MFA on registrar, GitHub, cloud and email accounts.
  • Use least-privilege IAM roles and separate production access.
  • Keep database services private where practical.
  • Use secret managers instead of source-code credentials.
  • Configure firewall/security-group rules deliberately.
  • Enable security logs and alerts for suspicious activity.
  • Use HTTPS end-to-end and renew certificates automatically.
  • Protect backups and test restoration.

13.3 Common attacks to understand

ThreatMeaningPrimary protection
SQL injectionUntrusted input changes the meaning of a database query.Parameterized queries, least privilege, validation.
XSSAttacker-controlled script runs in another user's browser.Output encoding, safe templating, CSP as defence in depth.
CSRFA browser is tricked into sending an unwanted authenticated request.CSRF tokens, SameSite cookies, origin checks as appropriate.

14. Performance, caching and reliability

14.1 Frontend performance

  • Resize and compress images; use WebP or AVIF where suitable.
  • Minify production CSS and JavaScript where your build process supports it.
  • Remove unused code and avoid loading large libraries unnecessarily.
  • Lazy-load below-the-fold images, but do not lazy-load the main hero image if it delays the visible page.
  • Set image dimensions to reduce layout shifts.
  • Use browser caching for versioned static assets.

14.2 Backend and database performance

  • Use database indexes for frequent filters, joins and lookups, then verify with query plans.
  • Use connection pooling and sensible timeouts.
  • Paginate large result sets.
  • Avoid repeated queries inside loops (N+1 query patterns).
  • Cache only data whose freshness rules are understood.
  • Set request size limits and protect expensive endpoints with rate limits.

14.3 Core Web Vitals

Learn Largest Contentful Paint (LCP), Interaction to Next Paint (INP) and Cumulative Layout Shift (CLS). Test with PageSpeed Insights and real-user data where available. A lab score is useful for diagnosis but is not the same as every visitor's real experience.

14.4 CDN and cache invalidation

A Content Delivery Network (CDN) caches eligible assets at edge locations. Use long cache lifetimes for fingerprinted static assets such as app.a83f2.js, and shorter or revalidated caching for HTML that changes frequently. Do not cache private, personalized responses publicly.

15. Monitoring, backups and ongoing maintenance

15.1 What to monitor

  • Uptime and external availability checks.
  • HTTP 4xx/5xx rates and application exceptions.
  • CPU, memory, disk, network and database connections.
  • Database storage, slow queries, failed connections and backup status.
  • Certificate expiry, domain renewal and email delivery failures.
  • Unexpected billing changes and resource usage.

15.2 Backup and recovery plan

Define Recovery Point Objective (RPO): how much data loss in time you can tolerate. Define Recovery Time Objective (RTO): how long the service can remain unavailable. Choose backup frequency and retention based on these objectives and the importance of the data.

  1. Enable automated database backups and confirm retention settings.
  2. Back up application configuration and required uploaded files.
  3. Protect backups from ordinary application credentials and accidental deletion.
  4. Document restoration steps and who is authorized to perform them.
  5. Practise restoring into a separate environment.
  6. Record the restore result and fix gaps before relying on the plan.

16. Final production launch checklist

Do not announce the site until the relevant items below have been checked.

Domain and network

  • Domain registration and renewal ownership confirmed.
  • Root domain and www resolve to the intended destination.
  • DNS records have been checked; old/unused records removed safely.
  • HTTP redirects to HTTPS and certificate covers every public hostname.

Application and database

  • Production build tested on staging.
  • Backend uses production environment settings and correct listening port.
  • Database is not publicly exposed without a compelling, secured design.
  • Application database identity has limited permissions.
  • Secrets are stored outside the repository.
  • Registration forms have server-side validation and safe error handling.
  • Email notifications tested, including spam/delivery checks.

Security and privacy

  • Admin accounts use MFA and least privilege.
  • Protected pages and records require server-side authorization.
  • Common injection, XSS, CSRF and access-control risks reviewed.
  • Privacy notice and data retention process reviewed for the information collected.
  • Logs do not expose passwords, tokens or sensitive personal data.

SEO and quality

  • Unique page titles, useful descriptions and semantic headings.
  • Mobile layout and keyboard navigation tested.
  • robots.txt and sitemap.xml reviewed.
  • Canonical hostname and URL strategy selected.
  • Search Console domain verified and sitemap submitted.
  • Broken links, missing images and browser console errors checked.

Operations

  • Automated backups enabled and a restore tested.
  • Uptime and error monitoring configured.
  • Billing budget and alerts configured.
  • Rollback/redeployment procedure documented.
  • Domain, cloud and repository account recovery protected with MFA.
Launch gate: every critical security, data, HTTPS, backup and recovery item must pass. If one fails, delay public launch and fix it. A site that loads is not automatically production-ready.
