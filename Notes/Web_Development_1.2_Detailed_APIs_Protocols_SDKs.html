APIs, Network Protocols & SDKs

A deeper technical branch: each API architecture, network protocol and SDK category is examined separately, including its purpose, operation, common use cases, methods, formats and design considerations.

How to use these notes
This is not a general introduction. Treat each numbered technology as its own topic. Compare it with the others, pay attention to what belongs to the application layer versus the transport layer, and distinguish a protocol's rules from the data format carried inside its messages.
PART I

API TYPES AND ARCHITECTURES

This section examines API styles individually. Each subsection explains what the API is, how communication works, where it is commonly used, the operations or methods involved, data formats, strengths, limitations and an example.

1. REST APIs (Representational State Transfer)

What it is

REST is an architectural style for designing networked services. A REST API exposes resources—such as students, products, orders or inquiries—through identifiable URLs. REST is not a programming language, a file format or a protocol. It commonly uses HTTP, but REST describes design constraints placed on the service.

How it works

A client addresses a resource using a URI/URL and sends an HTTP request. The request includes a method, headers and, when needed, a body. The server interprets the method against the resource, applies validation and business rules, accesses data if necessary, and returns an HTTP response containing a status code, headers and often a representation of the resource. REST emphasizes stateless requests: each request should contain the information needed to understand it, rather than depending on hidden server-side conversation state.

Where it is commonly used

REST is widely used for public web APIs, mobile-app backends, e-commerce systems, school portals, booking systems, dashboards, payment integrations and communication between microservices. It is a common default when different clients need predictable access to server resources.

HTTP methods commonly used

GET retrieves a representation; POST submits data or creates a subordinate resource; PUT replaces a resource representation; PATCH applies a partial update; DELETE removes a resource. HEAD requests headers without the response body; OPTIONS asks about communication options, often including CORS preflight. GET is intended to be safe; GET, HEAD, PUT and DELETE are defined as idempotent in HTTP semantics. POST is not generally idempotent.

Data formats accepted

REST itself does not mandate JSON. JSON is the most common response/request format in modern web APIs. XML may be used in older or enterprise integrations. Form URL-encoded data is common for simple form submissions; multipart/form-data is used for file uploads; plain text or binary formats may be used for specialized resources. The Content-Type header describes the request body format, while Accept communicates preferred response formats. The server must document which media types it supports.

Example endpoint design

GET /api/students/42 retrieves student 42. POST /api/students creates a student using a JSON body. PATCH /api/students/42 updates selected fields. DELETE /api/students/42 removes the resource if the caller is authorized.

Advantages and limitations

Advantages: familiar HTTP semantics, broad tooling, cache support, straightforward browser integration and loose coupling. Limitations: clients may receive more or less data than needed; several requests may be needed to assemble related data; teams must design consistent endpoints, pagination, filtering, versioning and error responses.

Key design practices

Use nouns for resource paths; choose status codes accurately; validate all input on the server; paginate large collections; document schemas; protect endpoints with HTTPS and appropriate authentication/authorization; avoid exposing internal database structure; and make retry behavior safe where possible.

2. SOAP APIs (Simple Object Access Protocol)

What it is

SOAP is a formal messaging protocol for exchanging structured information between systems. It commonly uses XML messages and a service contract, often described using WSDL (Web Services Description Language). Unlike REST, SOAP is a protocol with defined message structure and processing rules.

How it works

A client constructs a SOAP envelope containing an optional Header and a required Body. The body carries the operation request or response. The message is sent through a transport such as HTTP or HTTPS; other bindings are possible. The service reads the XML envelope, checks the requested operation and any required headers, performs the operation and returns a SOAP response or Fault describing an error.

Where it is commonly used

SOAP is found in enterprise integration, banking, insurance, government systems, payment infrastructure and older systems where strict contracts, formal operations and established WS-* standards are important. It remains relevant where organizations already depend on SOAP services.

Operations and HTTP methods

SOAP operations are defined by the service contract, not by REST-style resource methods. Over HTTP, SOAP 1.1 commonly uses POST and a SOAPAction header; SOAP 1.2 commonly uses POST with an action parameter where applicable. The HTTP method is a transport binding detail; the operation name is carried in the SOAP message body.

Data formats

SOAP messages use XML with a defined Envelope structure. XML Schema (XSD) can define the types and structure of message elements. Attachments can be handled using mechanisms such as MTOM/XOP. JSON is not the native SOAP message format.

Advantages and limitations

Advantages: strict contracts, mature tooling, formal error structures, extensibility through WS-* specifications and support for enterprise requirements. Limitations: verbose XML, more complex tooling, heavier messages and a steeper learning curve than many JSON REST APIs.

Key terms

Envelope: outer SOAP message structure. Header: metadata such as security or routing information. Body: operation payload. Fault: structured error. WSDL: machine-readable service contract. XSD: schema language used to define XML data structures.

3. GraphQL APIs

What it is

GraphQL is a query language for APIs and a runtime for executing those queries against a defined schema. It allows a client to request specific fields and related data, rather than requiring the server to expose a separate URL for every resource shape.

How it works

The server defines a schema containing types and fields. A client sends a query describing the data it wants. Resolver functions determine how each requested field is obtained, perhaps from a database or another API. The server returns a JSON response whose data shape follows the query. Mutations are used for operations that change data; subscriptions can support ongoing updates when the server and transport support them.

Where it is commonly used

GraphQL is used in complex frontend applications, mobile applications, content platforms and systems that combine data from several services. It is useful when different screens need different combinations of related fields or when clients need to reduce over-fetching and under-fetching.

Operations and HTTP methods

The three main operation types are Query (read), Mutation (change data) and Subscription (receive ongoing updates). Queries and mutations are commonly sent using HTTP POST; some servers also support GET for queries. Subscriptions commonly use WebSocket or another supported streaming transport. These are GraphQL operation types, not direct equivalents of all HTTP methods.

Data formats

GraphQL requests and responses are commonly represented as JSON. A request body often contains a query string, optional variables and an optional operation name. GraphQL is not itself a file format. File uploads require an agreed server-specific approach, commonly multipart request conventions or a separate upload endpoint.

Advantages and limitations

Advantages: clients select fields, related data can be fetched in one request, and a strongly typed schema supports introspection and tooling. Limitations: caching can be less straightforward than ordinary REST GET caching; poorly controlled queries can be expensive; authorization must be enforced at field/resolver level where appropriate; and schema governance requires discipline.

Example

A client might query a student name and the names of their enrolled courses in one operation. The response contains only the fields requested, rather than every field stored for the student and courses.

4. RPC APIs and gRPC

What it is

RPC means Remote Procedure Call: a client invokes an operation that is executed by another process or machine. gRPC is a modern, high-performance RPC framework originally developed by Google. It commonly uses Protocol Buffers (Protobuf) to define services and serialize messages.

How it works

A developer defines service methods and message types in a .proto contract. Code-generation tools create client and server interfaces. The client calls a generated method; gRPC serializes the request, sends it over HTTP/2, and the server deserializes it, runs the method and returns a serialized response. gRPC supports unary calls and streaming patterns.

Where it is commonly used

gRPC is common in internal microservice communication, backend-to-backend systems, cloud infrastructure and environments where efficient typed contracts and streaming are valuable. Browser use is possible through gRPC-Web with supporting infrastructure, but ordinary browsers do not expose every native gRPC capability directly.

Operations and methods

RPC APIs are organized around named procedures such as GetStudent, CreateStudent or StreamUpdates. gRPC commonly uses HTTP/2 POST requests underneath. The application-level method name is defined in the service contract; it is not selected from GET, POST, PUT and DELETE in the same resource-oriented way as REST.

Data formats

Native gRPC commonly uses Protocol Buffers, a compact binary serialization format. The .proto file defines messages and service methods. gRPC-Web has its own browser-compatible transport conventions. JSON can be supported by gateways or transcoding, but it is not the default native gRPC wire format.

Advantages and limitations

Advantages: compact messages, generated strongly typed clients, HTTP/2 multiplexing and support for streaming. Limitations: binary payloads are less human-readable, browser integration may need a proxy or gRPC-Web, and debugging can require specialized tools.

Streaming types

Unary: one request and one response. Server streaming: one request followed by multiple responses. Client streaming: multiple requests followed by one response. Bidirectional streaming: both sides send multiple messages over one call.

5. WebSocket APIs

What it is

A WebSocket API provides a persistent, two-way communication channel between a client and server. Unlike the usual request-then-response pattern of HTTP, either side can send a message whenever the connection is open.

How it works

A client begins with an HTTP handshake requesting an upgrade to the WebSocket protocol. If accepted, the connection changes to a WebSocket connection. The client and server exchange frames over that connection until it is closed. The application defines the message format and event meanings.

Where it is commonly used

Live chat, multiplayer games, collaborative editing, live dashboards, trading displays, monitoring systems, notifications and real-time tracking are common use cases.

Methods and operations

WebSocket is not built around REST HTTP methods after the connection is established. The browser WebSocket API provides operations such as connect, send, receive messages and close. The initial handshake uses HTTP Upgrade semantics; after that, WebSocket frames carry messages.

Data formats

WebSocket frames can carry text or binary data. JSON text is popular because it is easy to inspect; binary payloads may use formats such as Protobuf or application-specific bytes. WebSocket does not force one message format.

Advantages and limitations

Advantages: low-latency server push, full-duplex communication and less repeated connection setup. Limitations: connection management, authentication, scaling, reconnection, heartbeat/ping handling and message validation require careful design. A persistent connection consumes server resources.

Example event flow

A browser connects to /live. The server sends a JSON event when a new inquiry arrives. The browser receives the message and updates the dashboard without polling the server repeatedly.

6. Webhooks (Event Callback APIs)

What it is

A webhook is an event-driven HTTP callback. Instead of an application repeatedly asking whether something has changed, a provider sends an HTTP request to a URL registered by the receiving application when a specified event occurs. A webhook is a delivery pattern, not a separate transport protocol.

How it works

The receiver exposes a public HTTPS endpoint and registers it with the provider. When an event occurs, the provider sends an HTTP request—commonly POST—with an event payload. The receiver verifies the sender, validates the payload, processes it safely and returns a response. Providers often retry failed deliveries, so receivers should handle duplicate events.

Where it is commonly used

Payment notifications, repository events, form submissions, shipping updates, identity-provider events and automation platforms commonly use webhooks.

Methods and formats

Providers commonly send POST requests. JSON is the dominant payload format, though the provider's documentation determines the actual Content-Type and schema. The receiver should not assume every webhook uses the same fields or signature method.

Security and reliability

Use HTTPS; verify signatures or other provider authentication; check timestamps where supported; protect against replay; validate event IDs; make processing idempotent; respond promptly; and queue longer work. Never trust a webhook merely because it reached the endpoint.

Webhook vs polling

Polling means the client asks repeatedly for updates. A webhook means the provider pushes an event when something happens. Webhooks can reduce unnecessary requests, but require a reachable receiver and robust retry/security handling.

PART II

NETWORK PROTOCOLS

A protocol is a rule set for communication. These subsections separate application protocols from transport, internet and security protocols, and explain the role each plays in a complete network exchange.

1. HTTP — Hypertext Transfer Protocol

What it is

HTTP is an application-layer request-response protocol used to transfer web resources and API messages. It defines methods, status codes, headers, message framing and semantics.

How it works

A client sends a request containing a method, target, headers and optional body. A server or intermediary returns a status line/status, headers and optional content. HTTP is stateless at the protocol level; cookies, tokens and application logic can maintain user sessions.

Versions and transport

HTTP/1.1 commonly uses TCP and supports persistent connections. HTTP/2 uses TCP with binary framing and multiplexed streams. HTTP/3 uses QUIC over UDP, reducing some connection and transport-level head-of-line blocking issues. These versions retain HTTP semantics while differing in transport and framing.

Common methods

GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS and TRACE are defined methods. CONNECT is used to establish a tunnel, commonly through a proxy. Method semantics matter: safe methods should not be used to trigger state changes, and idempotency matters for retries.

Message formats

HTTP itself can carry many media types. Common Content-Type values include application/json, application/xml, text/html, text/plain, application/octet-stream, application/x-www-form-urlencoded and multipart/form-data. HTTP does not mean JSON; JSON is just one possible representation.

Where used

Websites, REST APIs, GraphQL over HTTP, downloads, uploads, service-to-service communication and many cloud integrations.

Important headers

Host identifies the target authority in HTTP/1.1; Content-Type describes the body; Accept describes acceptable response media types; Authorization carries credentials; Cache-Control guides caching; Origin is important in browser cross-origin requests; and Cookie/Set-Cookie support browser state.

2. HTTPS and TLS

What they are

HTTPS is HTTP carried over a connection protected by TLS (Transport Layer Security). TLS is the security protocol; HTTPS is the secure use of HTTP over TLS.

How it works

The client and server negotiate TLS parameters and establish shared session keys during a handshake. The server normally presents a digital certificate so the client can verify the server's identity. Application data is then encrypted and integrity-protected. Certificate validation, hostname matching and trusted certificate authorities are important.

Where used

Virtually all modern websites and APIs, especially login, payments, personal data, administrative tools and any service exposed over the public internet.

Ports and methods

HTTPS commonly uses TCP port 443 for HTTP/1.1 and HTTP/2 over TLS. HTTP/3 uses QUIC over UDP, commonly on port 443. HTTP methods remain GET, POST, PUT, PATCH and others; TLS does not define API methods.

Data formats

TLS encrypts transport data and does not prescribe whether the application payload is JSON, XML, HTML, images or binary data.

Security boundaries

TLS protects data in transit between endpoints. It does not automatically make an application secure, validate input, prevent authorization flaws, encrypt data stored on a server or protect a compromised device.

3. TCP — Transmission Control Protocol

What it is

TCP is a connection-oriented transport-layer protocol that provides a reliable, ordered byte stream between application endpoints.

How it works

A connection is established through a handshake. TCP numbers bytes, acknowledges received data, retransmits lost segments and uses flow and congestion control. Applications read a stream of bytes; message boundaries must be defined by the application protocol.

Where used

HTTP/1.1, HTTP/2, SSH, SMTP, IMAP, database connections and many other applications use TCP.

Ports and data

TCP uses port numbers to identify application endpoints. It carries bytes, not a particular file format. HTTP, SMTP or a database protocol defines how those bytes are interpreted.

Strengths and trade-offs

Reliable ordered delivery simplifies application development. Retransmission and ordering can add latency, and a lost segment can delay later data in the same stream. TCP does not encrypt data by itself.

4. UDP — User Datagram Protocol

What it is

UDP is a connectionless transport-layer protocol that sends independent datagrams. It provides port-based multiplexing and a checksum, but not TCP-style guaranteed delivery, ordering or retransmission.

How it works

An application sends a datagram to a destination IP address and port. UDP adds a small header and passes it to IP. The receiver may receive it, receive it late, receive it out of order or not receive it at all. Applications add reliability or timing behavior if they need it.

Where used

DNS queries, real-time voice/video, online games, live media and protocols such as QUIC commonly use UDP.

Data formats

UDP carries datagrams; the application protocol defines their contents. It does not require JSON, XML or any other file format.

Strengths and trade-offs

Low overhead and no built-in connection setup can suit latency-sensitive traffic. The application must manage loss, ordering, congestion and security as appropriate.

5. IP — Internet Protocol (IPv4 and IPv6)

What it is

IP provides logical addressing and routing so packets can travel between networks. IP is a network-layer protocol and does not guarantee delivery or application-level ordering.

How it works

The sender places data into IP packets with source and destination addresses. Routers forward packets toward the destination using routing information. Packets may take different paths; higher-layer protocols handle reliability when required.

IPv4 vs IPv6

IPv4 uses 32-bit addresses, for example 192.0.2.25. IPv6 uses 128-bit addresses, for example 2001:db8::25. IPv6 offers a much larger address space and changes aspects of addressing and network configuration.

Where used

Everyday internet communication, local networks, cloud hosting, mobile networks and communication between services.

What it does not do

IP does not define HTTP methods, JSON structure, user authentication or guaranteed delivery. Those responsibilities belong to other layers and application protocols.

6. DNS — Domain Name System

What it is

DNS is a distributed naming system that maps domain names to records used to locate services and publish domain-related information.

How it works

A device asks a DNS resolver for a record. The resolver may answer from cache or query DNS infrastructure, following referrals until it obtains an answer. The result is cached according to its Time To Live (TTL). The application then uses the resolved information to contact the service.

Important record types

A maps a name to an IPv4 address; AAAA maps to IPv6; CNAME provides an alias; MX identifies mail exchangers; TXT stores text data used for verification and email policies; NS identifies authoritative name servers; and SRV can describe service locations and ports.

Where used

Website access, email routing, service discovery, domain verification and infrastructure configuration.

Ports and transport

Traditional DNS commonly uses UDP port 53 for queries and TCP port 53 for cases such as large responses and zone transfers. DNS over TLS commonly uses port 853; DNS over HTTPS commonly uses HTTPS, often port 443.

Important distinction

DNS resolves names; it does not fetch the web page. The browser still needs to establish a connection and make an HTTP request.

7. SSH and SFTP

What they are

SSH (Secure Shell) provides encrypted remote login and command execution. SFTP (SSH File Transfer Protocol) is a file-transfer protocol that operates over SSH. SFTP is not the same protocol as FTP or FTPS.

How they work

An SSH client connects to an SSH server, normally on TCP port 22. The parties negotiate cryptographic algorithms and establish an encrypted session. The user authenticates, commonly with a password or public-key authentication. SFTP uses the secure SSH channel to list, upload, download, rename and manage files.

Where used

Remote server administration, secure file exchange, deployment workflows, backups and controlled transfers between organizations.

Data formats and commands

SSH is a secure channel, not a file format. SFTP transfers files as bytes and can transfer JSON, CSV, images, archives or other file types without interpreting their contents.

Security practices

Verify host keys, use strong key protection, restrict accounts and permissions, disable weak authentication options and avoid exposing SSH to unnecessary networks.

8. FTP and FTPS

What they are

FTP (File Transfer Protocol) is a traditional file-transfer protocol. FTPS is FTP protected with TLS. FTP and SFTP are different protocols despite their similar names.

How they work

FTP uses a control connection for commands and a separate data connection for transfers. Active and passive modes determine how data connections are established. FTPS adds TLS protection to the relevant connections, with explicit and implicit configurations seen in deployments.

Where used

Legacy hosting, managed file-transfer environments and organizations with established FTP-based workflows.

Ports and formats

FTP control commonly uses TCP port 21; data connections depend on mode and server configuration. FTP transfers file bytes and does not require a particular file format.

Limitations

Plain FTP does not encrypt credentials or data. Firewalls and NAT can complicate separate data connections. Prefer SFTP or properly configured FTPS when secure file transfer is required.

9. SMTP, IMAP and POP3 — Email protocols

SMTP — sending email

SMTP (Simple Mail Transfer Protocol) is used to submit and relay outgoing email between clients and mail servers or between mail servers. Common ports include 25 for server relay, 587 for message submission with STARTTLS commonly used, and 465 for implicit TLS submission.

IMAP — synchronized mailbox access

IMAP (Internet Message Access Protocol) lets clients access and manage messages stored on a mail server. It supports folders, message flags and synchronization across multiple devices. Common ports are 143 (often upgraded with STARTTLS) and 993 (implicit TLS).

POP3 — mailbox retrieval

POP3 (Post Office Protocol version 3) retrieves messages from a mailbox and generally offers simpler mailbox management than IMAP. Common ports are 110 and 995 for implicit TLS.

Formats and relationship

Email messages use Internet Message Format, with headers and a body. MIME (Multipurpose Internet Mail Extensions) supports attachments and non-ASCII content. SMTP sends; IMAP and POP3 retrieve or access stored messages. They are complementary, not interchangeable.

Where used

Email clients, mail servers, business notifications, support systems, account verification and automated application emails.

10. WebSocket protocol

What it is and how it works

WebSocket is an application-layer protocol for full-duplex communication over a persistent connection. A client requests an HTTP upgrade; the server accepts; then both sides exchange WebSocket frames until closure.

Where used

Chat, live dashboards, collaboration, game state, live tracking and push updates.

Ports and formats

WebSocket commonly uses port 80 (ws) or 443 (wss). Text frames often contain JSON; binary frames can contain arbitrary binary data. The protocol does not impose one application payload format.

Operational concerns

Implement authentication, authorization, origin checks, message-size limits, rate limits, ping/pong heartbeats, reconnect logic and horizontal-scaling strategy.

11. QUIC

What it is

QUIC is a secure, multiplexed transport protocol built over UDP. It is the transport used by HTTP/3.

How it works

QUIC integrates TLS 1.3 handshake mechanisms, stream multiplexing, loss recovery and connection migration. Separate streams can progress independently, reducing transport-level head-of-line blocking between streams compared with a single TCP byte stream.

Where used

HTTP/3 web traffic, modern browsers, CDNs and services that benefit from fast connection setup and resilient transport.

Ports and formats

QUIC commonly uses UDP port 443 for HTTP/3. It carries streams and datagrams; HTTP defines the application messages and content formats above it.

Important distinction

QUIC is not the same as HTTP/3. QUIC is the transport; HTTP/3 is the HTTP mapping that uses QUIC.

PART III

SDK TYPES AND DEVELOPMENT KITS

An SDK is a packaged development toolkit. SDK categories are often defined by the platform, service, language or hardware being targeted. The categories can overlap: a single product may provide a platform SDK and service-specific SDK libraries.

1. Platform SDKs

What they are

Platform SDKs provide tools and interfaces for building software for a particular operating system, device platform or runtime environment.

Typical contents

Platform APIs, libraries, compilers or build tools, headers, documentation, emulators/simulators, debugging tools and packaging utilities.

Examples and use

Android SDK for Android applications; Apple SDKs for iOS, macOS and other Apple platforms; Windows SDK for Windows applications. Developers use them when an application must access platform capabilities such as sensors, notifications, storage, graphics or system services.

Workflow

Install the supported SDK version, configure the development environment, select a target platform/API level, build against the platform interfaces, test on an emulator or real device, and package the application for distribution.

Trade-offs

Platform SDKs provide direct access to native features but may tie code to a platform and require version-specific testing.

2. Cloud and service SDKs

What they are

Cloud/service SDKs make it easier for an application to use a provider's hosted services, such as storage, databases, messaging, identity, analytics or maps.

Typical contents

Service clients, authentication helpers, request signing, retry logic, pagination helpers, data models, configuration utilities and examples.

Examples and use

Cloud-provider SDKs for storage or compute; Firebase SDKs for application services; mapping SDKs for maps and location. They are used when an application needs to call a provider's services without manually implementing every API request.

How they work

The developer installs a package, configures a client with the required endpoint/region/credentials, calls library methods, and the SDK constructs network requests, handles serialization and returns results or errors.

Security

Do not embed privileged server credentials in browser or mobile application code. Use restricted client keys where designed for public use, and keep privileged operations behind a trusted backend.

3. Programming-language SDKs

What they are

A language-specific SDK or developer kit supplies APIs, libraries, tooling and conventions for using a platform or service from a particular programming language.

Examples and use

A service may provide separate JavaScript, Python, Java, C# or Go SDK packages. Each package presents language-appropriate methods, types, asynchronous patterns and error handling.

How they work

The package manager installs the dependency. The developer imports or references it, configures it and calls its functions/classes. The SDK may then make HTTP requests, serialize messages or interact with local platform tools.

Important distinction

A language package is not automatically a complete SDK. Some are only libraries or API clients. Check what tools and capabilities are actually included.

4. Hardware and device SDKs

What they are

Hardware SDKs help applications communicate with a particular device, board, sensor, camera, printer, scanner, vehicle system or embedded platform.

Typical contents

Device drivers or wrappers, communication libraries, firmware utilities, sample code, protocols, debugging tools and hardware documentation.

Where used

Internet of Things (IoT), robotics, industrial automation, point-of-sale systems, medical devices, cameras and specialized peripherals.

How they work

The application uses SDK functions to communicate through an interface such as USB, Bluetooth, serial communication, Wi-Fi or a vendor-specific network protocol. The SDK hides some low-level commands but the developer must still manage device availability, permissions, timeouts and errors.

Trade-offs

Hardware SDKs can simplify complex device integration but may be vendor-specific and dependent on firmware, operating system and hardware revisions.

5. Game development SDKs

What they are

Game SDKs provide tools or service integrations for game development, publishing, multiplayer, input, audio, graphics, achievements, analytics or platform distribution.

Examples and use

Game engine toolkits and platform SDKs for console/mobile publishing; multiplayer networking SDKs; audio and physics libraries; analytics and achievement services.

Typical contents

APIs, runtime libraries, editor integrations, asset tools, emulators, profiling and debugging utilities, sample projects and documentation.

Selection considerations

Check target platforms, performance overhead, licensing, engine compatibility, online-service dependencies, player privacy and long-term support.

6. SDK vs API vs library vs framework — detailed distinction

API

The interface contract: the available operations, inputs, outputs and rules. An API may be local (inside a program) or remote (over a network).

Library

Reusable implementation code that a developer calls. A JSON parsing library, for example, can parse JSON but does not necessarily provide a complete development environment.

Framework

A larger structure that organizes an application and often invokes developer-written code through lifecycle hooks or conventions. The framework commonly controls the flow of execution.

SDK

A development kit that may bundle APIs, libraries, frameworks, command-line tools, documentation, emulators, compilers or debugging utilities.

How they fit together

A platform SDK may expose platform APIs, include libraries and provide command-line build tools. An application uses those components to call platform features. The API is the contract; the library provides reusable code; the SDK is the broader kit.

7. How to evaluate and integrate an SDK

Before installation

Confirm the SDK's official source, supported language/runtime versions, platform compatibility, license, maintenance status, security advisories, package size and whether it is necessary.

During integration

Use the official installation instructions and a supported version. Store secrets appropriately, configure only required permissions, inspect default telemetry/data collection and start with a minimal example.

Testing

Test normal responses, invalid input, permission denial, network interruption, expired credentials, rate limits, large payloads and unsupported versions. Confirm that failures are surfaced clearly.

Maintenance

Pin or constrain dependency versions, review release notes, update security fixes, remove unused packages and plan a migration path in case the provider changes or the SDK is discontinued.

CONSOLIDATION

Comparative review and practical tasks

Do not confuse these concepts

  • REST is an architectural style; HTTP is an application protocol commonly used to implement REST APIs.
  • JSON is a data format, not an API type or network protocol.
  • TCP and UDP are transport protocols; they do not define API operations or JSON fields.
  • TLS protects a connection; HTTPS is HTTP secured with TLS.
  • GraphQL Query/Mutation are GraphQL operation types, not HTTP methods.
  • gRPC is an RPC framework; Protocol Buffers are a common serialization format it uses.
  • Webhooks are an event-delivery pattern, usually implemented using HTTP requests.
  • SDK is a toolkit; it may contain libraries, API clients, command-line tools and documentation.

Practical tasks

  1. Design a REST API for student admissions. Define endpoints for listing, creating, viewing, updating and deleting an inquiry. Select HTTP methods, request formats and response status codes.
  2. Write a short comparison of REST, SOAP, GraphQL and gRPC. For each, state its message format, communication pattern and a suitable use case.
  3. Trace a browser request from domain lookup through transport connection and HTTPS protection to the HTTP response. Identify the role of DNS, IP, TCP or QUIC, TLS and HTTP.
  4. Choose a live-chat feature and explain why WebSocket may be more appropriate than repeated polling.
  5. Explain how a payment webhook should verify its sender and safely handle duplicate event delivery.
  6. Choose a mobile or cloud SDK. Identify its target platform/service, included tools, installation approach, credentials and security precautions.

Knowledge-check questions

  1. Why is REST not the same thing as HTTP?
  2. Which HTTP method is normally used to partially update a REST resource?
  3. Does REST require JSON? Explain.
  4. What does a SOAP Envelope contain?
  5. How do GraphQL queries differ from mutations?
  6. What is a Protocol Buffer and why is it used by gRPC?
  7. What happens during a WebSocket upgrade?
  8. Why should webhook handlers be idempotent?
  9. What is the difference between TCP reliability and UDP datagram delivery?
  10. What is the difference between HTTPS and TLS?
  11. What is the difference between SFTP and FTPS?
  12. Which email protocol sends messages, and which protocols access a mailbox?
  13. What is the difference between an SDK and a library?
Study reminder: For every technology, be able to answer six questions: What is it? How does it work? Where is it used? What methods or operations does it expose? What data does it carry or accept? What are its strengths, limitations and security concerns?
